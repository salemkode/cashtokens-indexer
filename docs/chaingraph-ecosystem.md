# CashTokens data infrastructure: ecosystem research

Reviewed 14 November 2026. Sources are project-owned repositories, documentation, and release announcements. Repository integration proves that code uses an API; it does not independently prove a particular production deployment's present configuration or uptime. CashTokens and legacy SLP are different protocols; this report concerns CashTokens.

The strongest relevant findings are that **Cashonize already separates ordinary wallet data from Chaingraph**, **Rostrum offers more token indexing than basic Fulcrum**, and **TokenStork already runs a purpose-built token index directly against BCHN**. A replacement for the explorer can keep a small, explicit API rather than reproduce Chaingraph's general transaction graph.

## Alternatives worth evaluating

| Tool | Useful scope | Boundary for this explorer |
| --- | --- | --- |
| Fulcrum / Electrum Cash | [Protocol 1.5+](https://electrum-cash-protocol.readthedocs.io/en/latest/protocol-methods.html#blockchain-address-listunspent) includes token-bearing UTXOs with category, decimal-string amount, capability, and commitment. Known address/script holdings can be aggregated without a general graph service. `blockchain.utxo.get_info` checks whether a known output remains unspent. | Address-centric queries do not enumerate every holder of a category or provide global category supply/history. Its documented UTXO lookup returns null for a spent output rather than identifying the spender. BCH values returned by `get_balance` are satoshis, not aggregate fungible-token units. [Source repository](https://github.com/cculianu/Fulcrum). |
| Rostrum | The [official BCH protocol methods](https://nexa.gitlab.io/rostrum/protocol/methods/) include token address/script balances, token UTXOs, category transaction history, NFT commitment listings, genesis/BCMR locators, and `blockchain.utxo.get(txid,vout)` with spender details. | It is a real candidate for reusing existing token indexes. The listed API does not provide a ready-made global holder leaderboard or total live supply; those still need aggregation. NFT commitment listings describe identities observed, not a complete live NFT-owner table. Check exact server version and BCH result shapes. |
| TokenStork | Its [source and architecture](https://github.com/Panmoni/tokenstork/blob/2b346ff210b3699a0dfba51708d2dbee063b8bd9/README.md) describe an archival BCHN, Rust workers, Postgres, token UTXOs, materialized supply/holders, and a separate verified BCMR authchain walker. It explicitly avoids an external blockchain indexer. | Strong existing implementation to study or reuse, subject to its license and deployment needs. It is a larger analytics application than this explorer requires. Its single-VPS and performance statements are author reports, not measurements reproduced here. |
| Paytaca BCMR indexer | [README/API](https://github.com/paytaca/bcmr-indexer/blob/8c4071065693cc67b261d68dce541a1e64262233/README.md) exposes metadata, authchain head, NFT-type information, CashTokens listings, and indexed height. [`bchn.py`](https://github.com/paytaca/bcmr-indexer/blob/8c4071065693cc67b261d68dce541a1e64262233/bcmr_main/bchn.py) reads BCHN directly. | Useful metadata/authchain component or public data source; do not assume its metadata endpoints provide complete holder balances. Self-hosting adds its own application/database/worker stack. |
| OPTN TokenIndexer | The [operator's infrastructure page](https://www.optnlabs.com/ecosystem) advertises token balances, holders, metadata, and portfolio data, with mainnet/chipnet services. | A service candidate, not a verified drop-in API or cost-saving conclusion. Access terms, complete API contracts, implementation, and current pricing were not established in this review. |

Rostrum **15.0.0 was announced on 5 November 2026**, including cursor pagination and query/reorganization consistency changes. Its upgrade rebuilds the database, so switching is not an instantaneous server swap. [Official release announcement](https://forum.nexa.org/t/new-release-rostrum-15-0-0/1778). The [BCH build instructions](https://nexa.gitlab.io/rostrum/build/) require the BCH feature; Nexa token examples must not be copied as BCH response contracts.

`electrum-cash` and `@electrum-cash/network` are client libraries. Installing either does not create a server index or add missing category-wide methods.

## Recommended scope for a smaller backend

For the current explorer, keep a direct REST contract for category summary, live token UTXOs, aggregate holders, category history including complete burns, and script-level holdings. A BCHN-backed token-only SQLite index can serve this contract without Postgres, Hasura, or a full transaction graph. This is an architectural inference about component count, not a measured hosting-price or throughput comparison. The full node's storage and synchronization costs still exist.

Use Electrum for ordinary known-address BCH data, or evaluate Rostrum if its additional token history and spender indexes replace enough custom work. Reuse the same trusted node where practical. Measure on representative categories before claiming speed: warm/cold API latency, indexing throughput, index size, peak RAM, and reorganization recovery all matter. Browser rendering time and remote-node/network time are separate from local SQL execution time.

Correctness requirements for the small index remain substantial:

- Process every output and spend from a canonical block atomically, allowing BCH's CTOR order to put a spender before its parent transaction in the same block.
- Persist and verify network identity/checkpoints, restore spent UTXOs during rollback, and never mix mainnet and chipnet.
- Preserve integer quantities as decimal strings/BigInt, and aggregate a holder's entire balance before pagination.
- Keep confirmed-only data explicit until a separate mempool overlay handles arrivals, evictions, conflicts, and confirmation correctly.
- Treat BCMR as a separate provenance boundary: a registry's display name is not on-chain verification. Verified metadata needs authchain tracking plus matching the downloaded bytes to the committed hash.
- SLP needs its own OP_RETURN/DAG-validation rules; indexing CashTokens does not add legacy SLP support.

The requested explorer migration now removes Chaingraph from every page. BCH blocks, transactions and mempool data use direct BCHN-backed REST reads; address history and balances use Electrum. Token-only SQLite queries do not replace those BCH RPC/Electrum capabilities. Metadata remains public-registry data and explicit schema/hash diagnostics, without claiming verified authchain ownership.
